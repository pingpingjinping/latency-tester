# Rev3 음수 레이턴시 조사 기록 — 2026-10-29

이 문서는 당시 측정/계산 기준을 보존한 기록입니다. 이후 기본 표시를 바꾼 내용은 [기준 장비 맞춤 보정 기록](rev3-reference-calibration-2026-10-30.md)에 있습니다.

## 현재 상태와 결정

음수를 양수로 접어 보이게 만드는 절댓값이나 임의의 고정 보정값은 채택하지 않았다. IN 완료를 실제 접점 작동 시각으로 확정할 수 없으며, USB 왕복의 중간점도 검증되지 않았다.

화면은 연결·측정 설정·평균/범위·그래프·CSV의 기본 구성으로 정리했다. 버전 통신·설명자·수신 순서 비교 버튼과 여러 중간점 추정 패널은 제거했다. 해당 실험 코드와 원본 파일은 조사 재현을 위해 남긴다.

Rev3 기본 측정은 **IN 수신 먼저 등록 → 기존 contact_once 명령 OUT** 순서다. 표시값은 OUT 요청부터 입력 처리까지의 시간이며 테스터 작동 지연을 포함한다. 키보드만의 지연으로 이름 붙이거나, 이번 변경으로 음수가 반드시 사라진다고 주장하지 않는다.

## 환경과 시각 정의

- 테스터: RAKKA Rev3, VID `5249`, PID `4C65`, 사용자가 확인한 MCU CH32V203C8T6.
- 대상: 사용자 GMK70. 유선·2.4GHz·Bluetooth를 비교한 뒤 주로 유선으로 조사했다.
- 브라우저: 사용자 PC의 WebUSB 측정. 키 입력은 브라우저 이벤트로 관측한다.
- USB 포트/허브 영향도 의심했으나 포트만 바꾼 통제 실험으로 원인을 확정하지 않았다.
- 아래 수치는 보관 CSV 각각에서 재계산했다. 채팅에 붙여 넣은 앞선 별도 실행 결과와 같은 회차로 합치지 않았다.

| 기호 | 호스트에서 기록한 시각 |
| --- | --- |
| T0 | transferOut 호출 직전 |
| T1 | OUT 완료 콜백 |
| T2 | IN 완료 콜백 |
| Kd / Ku | keydown / keyup 처리 함수 실행 |
| Ed / Eu | 해당 이벤트의 event.timeStamp |
| H | 요청한 접점 유지시간 |

실제 접점 누름/뗌 시각은 이 로그에 없다. T0/T1/T2는 전기 신호를 직접 측정한 시각이 아니다.

## 확인한 계산식

| 방식 | Keydown | Keyup | 판단 |
| --- | --- | --- | --- |
| 원본 웹 코드의 IN 기준 | Kd−T2 | Ku−T2−H | 입력이 IN 완료보다 먼저 관측되면 음수 가능 |
| OUT 완료 기준 | Kd−T1 | Ku−T1−H | 다른 기준점의 참고값 |
| OUT 완료~IN 완료 중간점 | Kd−(T1+T2)/2 | Ku−H−(T1+T2)/2 | 원본에 (T2−T1)/2를 더하는 실험. 접점 기준으로 검증되지 않음 |
| OUT 요청~IN 완료 중간점 | Kd−(T0+T2)/2 | Ku−H−(T0+T2)/2 | 앞선 추정에 OUT 소요의 절반을 더함. 정확도 근거는 확보 못함 |
| 이벤트 시각 비교 | 위 식의 Kd를 Ed로 교체 | 위 식의 Ku를 Eu로 교체 | 이벤트 처리 대기를 분리하기 위한 진단 |
| 현재 기본 요청 기준 | Kd−T0 | Ku−T0−H | 테스터 작동 지연을 포함한 미보정 경과시간 |

입력이 늦어질수록 지연도 커져야 한다. 음수에 절댓값을 취하면 이 순서를 뒤집을 수 있으므로 결과나 식 중간에 절댓값을 넣는 방법은 채택하지 않았다.

## 처음 중간점 가설을 세운 배경

이전 README에 기록한 FUN60 Ultra 사례는 원본 IN 기준 Keydown 약 −6.89ms, OUT→IN 약 15.98ms였다. 절반을 더하면 약 1.10ms가 됐다. GMK70의 앞선 별도 실행에서는 원본 약 2.55ms, OUT→IN 약 16.09ms로 중간점 약 10.60ms였다. 사용자가 다른 테스터에서 본 대략적인 값과 비슷해 중간점 가설을 시험했다. 이는 유사한 수치라는 단서였으며 실제 접점 기준 검증은 아니었다. 해당 수치는 과거 README 기록이고, 아래 첨부 CSV 실행과 합산하지 않았다.

## 연결 방식 비교

각 파일은 50회 성공, 유지시간 20ms다. 단위는 ms, 표는 회차별 값을 평균했다.

| 실행 | 원본 IN Keydown | 원본 IN Keyup | OUT→IN 대기 | 기존 중간점 Keydown | 기존 중간점 Keyup |
| --- | ---: | ---: | ---: | ---: | ---: |
| 유선 1차 | −0.088 | −0.782 | 16.094 | 7.959 | 7.265 |
| 2.4GHz 1차 | 4.426 | 3.682 | 16.022 | 12.437 | 11.693 |
| Bluetooth 1차 | 11.404 | 7.942 | 16.072 | 19.440 | 15.978 |
| 유선 이벤트 기록 2차 | −0.366 | −1.096 | 15.990 | 7.629 | 6.899 |
| 2.4GHz 이벤트 기록 2차 | 4.596 | 4.218 | 15.984 | 12.588 | 12.210 |
| Bluetooth 이벤트 기록 2차 | 10.514 | 10.616 | 16.012 | 18.520 | 18.622 |

파일: [유선 1차](experiments/rev3-2026-10-29/gmk70-wired-round1.csv), [2.4GHz 1차](experiments/rev3-2026-10-29/gmk70-24g-round1.csv), [Bluetooth 1차](experiments/rev3-2026-10-29/gmk70-bluetooth-round1.csv), [유선 2차](experiments/rev3-2026-10-29/gmk70-wired-events-round2.csv), [2.4GHz 2차](experiments/rev3-2026-10-29/gmk70-24g-events-round2.csv), [Bluetooth 2차](experiments/rev3-2026-10-29/gmk70-bluetooth-events-round2.csv).

연결 방식에 따른 차이는 관측됐지만 모든 방식의 OUT→IN 대기는 약 16ms였다. 이 16ms를 키보드 고유 지연으로 취급할 수 없다.

## OUT 요청 시각까지 포함한 중간점

유선 1차에서 OUT 소요 평균은 12.700ms였다. 따라서 중간점 추정값은 Keydown 7.959→14.309ms, Keyup 7.265→13.615ms로 각각 6.350ms 증가했다. 값이 증가한 것은 수식의 기준점 이동이며 실제 접점 시각이나 정확도를 검증한 결과가 아니다.

## 이벤트 처리 지연과 유지시간 실험

유선 2차의 이벤트→처리 평균은 Keydown 0.222ms, Keyup 0.166ms였고 최대 0.4/0.3ms였다. 연결 방식/유지시간 실험에서도 처리 대기는 대체로 0.2ms 수준, 최대 0.5ms였다. 이 기록에서는 수십 ms 튐을 단순 처리 함수 대기만으로 설명할 수 없었다.

| 유지시간 | 성공/기록 | 원본 IN Keydown 평균 | 원본 IN Keyup 평균 | OUT→IN 평균 |
| --- | ---: | ---: | ---: | ---: |
| 10ms | 49/50 | −0.206 | −1.420 | 16.094 |
| 20ms, 유선 2차 | 50/50 | −0.366 | −1.096 | 15.990 |
| 50ms | 50/50 | 0.060 | −0.110 | 15.978 |
| 100ms | 50/50 | 0.622 | −1.438 | 16.000 |

파일: [10ms](experiments/rev3-2026-10-29/gmk70-wired-hold10.csv), [50ms](experiments/rev3-2026-10-29/gmk70-wired-hold50.csv), [100ms](experiments/rev3-2026-10-29/gmk70-wired-hold100.csv).10ms 파일의 실패 행은 버리지 않았다.

유지시간에 비례해 OUT→IN 대기가 증가하지 않았다. Keyup의 H 차감만을 원인으로 확정할 근거는 얻지 못했다.

## 접점 동작 없는 버전 통신

버전 명령 0만 반복하는 기존 순차 검사 50회도 응답 대기 평균 15.924ms, 중간값 16ms, OUT 평균 12.994ms, 전체 평균 28.918ms였다. 약 16ms 대기는 키보드 입력 없이도 나타났다.

[원본 버전 통신 CSV](experiments/rev3-2026-10-29/version-sequential.csv).완료 시각에서 약 8ms 간격의 위상 패턴이 관측됐지만, 호스트 타임스탬프만으로 실제 USB 동작 속도를 확정하지 않았다.

## USB 엔드포인트 설정

| --- | --- | --- | ---: | ---: |
| IN | 0x81 | interrupt | 64B | 8 |

## 버전 명령 수신 순서 비교

IN 요청을 먼저 등록하는 방식과 기존 OUT 완료 후 IN을 요청하는 방식을 각 5회 예열·50회 비교했다. 쌍마다 AB/BA를 교대했다. 총 100회 성공, 재전송 없음.

| 평균 | 기존 순차 | 수신 먼저 |
| --- | ---: | ---: |
| OUT 소요 | 12.256ms | 11.960ms |
| IN−OUT 완료 차이 | 16.054ms | −0.020ms |
| 양쪽 통신 완료까지 | 28.310ms | 11.962ms |

## 실제 접점 수신 순서 비교

GMK70 유선, 키 `1`, 유지 20ms, 간격 50ms. 각 방식 35회, 35쌍이 완료됐고 36번째 쌍의 기존 순서에서 입력 이벤트 시간 초과로 중지했다. 70회 성공과 실패 1행을 보관했다. 성공 행의 재전송은 없고 응답 명령/값은 모두 2/20이었다.

| 지표 | 기존 순차 | 수신 먼저 |
| --- | ---: | ---: |
| IN−OUT 완료 차이 평균 | 15.971ms | −0.006ms |
| 양쪽 통신 완료까지 평균 | 28.311ms | 12.614ms |
| IN 기준 Keydown 평균 | −0.200ms | −0.583ms |
| IN 기준 Keyup 평균 | 1.031ms | −0.780ms |
| IN 기준 Keyup 중간값 | −0.800ms | −1.000ms |
| Keydown 음수 회차 | 23/35 | 22/35 |
| Ed−T0 평균 | 27.837ms | 11.780ms |

[접점 비교 원본 CSV](experiments/rev3-2026-10-29/contact-order-comparison.csv).USB 대기뿐 아니라 OUT 요청 기준 입력 관측 시각도 약 16ms 당겨졌다. 따라서 줄어든 USB 대기를 키보드 지연에서 그대로 빼거나, 절반을 확정 보정값으로 쓸 수 없다. 수신 먼저에서도 음수가 남았다.

15번째 쌍의 기존 순서에서 Keyup 47.1ms가 관측됐다. 이벤트 시각 기준도 46.8ms이고 처리 대기는 0.3ms였다. 이 회차는 성공으로 저장됐으며 중지 원인은 아니다. 사용자는 GMK 기판에서 과거에도 가끔 튐이 있었다고 보고했다. 이 로그만으로 기판 원인까지 확정하지 않는다.

마지막 실패는 누름→뗌 한 쌍이 H+1000ms, 즉 1020ms 안에 완성되지 않은 경우다. 당시 실패 행에는 부분 시각이 없어 어느 입력이 누락됐는지 구분할 수 없었다. 정리 후 기본 측정에서는 실패 전 수신된 입력/USB 시각과 실패 단계를 CSV에 남긴다. 실패나 USB 오류 뒤에는 다음 Rev3 접점 명령을 자동으로 보내지 않는다.

## 새 기준과 남은 과제

물리적 키보드 지연을 추정하려면 다음 항을 분리해야 한다.

```text
누름 지연 = (Kd − T0) − D
뗌 지연   = (Ku − T0 − H) − D
D = OUT 요청부터 실제 접점 작동까지 걸린 시간
```

위 모델은 뗌 시각이 실제 누름+H이고 양쪽에 같은 D를 적용할 수 있다는 가정을 포함한다. 실제 누름/뗌 신호를 확인하면 두 기준을 각각 검증해야 한다.

현재 D는 미확정이며 0으로 측정된 것이 아니다. 기본 화면은 D를 빼기 전 경과시간만 표시한다. D를 USB 완료 시각·중간점·음수의 절댓값·관측 최솟값으로 자동 결정하지 않는다. 정확한 접점 시각 검증에는 접점 신호와 독립 기준의 추가 관측이 필요하다.

## 원본 보존과 코드

원본 CSV 12개와 설명자 JSON 1개는 [실험 파일 폴더](experiments/rev3-2026-10-29/)에 내용 변경 없이 복사했다. [manifest.json](experiments/rev3-2026-10-29/manifest.json)에 원래 이름·보관 이름·바이트 수·SHA-256이 있다. 실패 행이나 튀는 값도 삭제하지 않았다.

수신 순서 실험은 `rev3-diagnostics.mjs`, `contact-order.mjs`, 설명자 읽기는 `usb-descriptors.mjs`에 남아 있지만 기본 화면에는 연결하지 않는다. 기존 중간점 계산과 옛 CSV 함수는 과거 데이터 해석/회귀 검사용이며 새 기본 표시에는 쓰지 않는다. 새 기본 측정/CSV는 `measurement.mjs`다. 이전 UI와 계산 전체는 PR #17의 커밋 `b797518cf18899ee43029cc949fe2e99895fe6ff`에도 남아 있다.
